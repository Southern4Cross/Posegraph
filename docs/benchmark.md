# SAM 3D Body 显存/速度实测

- 日期：2026-10-24
- 硬件：RTX 4060 Laptop 8GB，驱动 595.97；PyTorch 2.11.0+cu128，Windows 11
- 模型：`sam-3d-body-vith`（魔搭镜像，SHA256 与 HF 官方一致）
- 输入：上游示例 `notebook/images/dancing.jpg`，整图作为人物框，无检测器、无 FOV 估计器，`inference_type=full`（含手部精修）
- 同时运行 FF14（`ffxiv_dx11.exe`），测试时游戏占用约 3.1GB

| 骨干精度 | 权重显存 | 峰值 reserved | 进程总占用 | 单张推理 | 首次加载 |
|---|---|---|---|---|---|
| bf16（上游默认） | 2977 MB | 3218 MB | ~3.3 GB | 1.35 s | 9 s |
| fp16 | 2978 MB | 3206 MB | ~3.3 GB | 1.38 s | 8 s |
| fp32 | 4245 MB | 4834 MB | ~4.1–4.8 GB | 1.99 s | 9 s |

显存构成（bf16）：backbone 1205 MB；head_pose 与 head_pose_hand 各 691 MB（其中各自加载了一份 662 MB 的 MHR TorchScript，内容相同）；decoder/decoder_hand 各 150 MB。

## 结论

- 能跑。bf16 与游戏同时运行时总占用约 6.4GB / 8GB（共用 MHR 后约 5.7GB，见下文）。
- 风险：游戏显存占用会波动（另一次观测为 4.35GB），叠加后逼近 8GB 时 Windows 会把显存溢出到系统内存，推理从 1.4 秒变成 10 分钟以上（实际遇到过）。
- fp16 相比 bf16 没有收益，保持上游默认 bf16。

## 优化：身体头/手部头共用一份 MHR（已默认开启，`share_mhr=True`）

上游 `head_pose` 与 `head_pose_hand` 各从同一个 `mhr_model.pt` 加载一份冻结的 TorchScript，代码中只做无状态前向（`mhr_head.py` 唯一调用点），因此可以共用。

**显存（bf16，同一时段 A/B，游戏运行中）**

| | 权重显存 | 峰值 reserved | 进程总占用 | 单张推理（5 次平均，两轮） |
|---|---|---|---|---|
| 不共用（上游原样） | 2977 MB | 3218 MB | ~3.31 GB | 1910 / 1957 ms |
| 共用 | 2311 MB | 2526 MB | ~2.64 GB | 1798 / 1897 ms |

节省约 670MB，推理不变慢。这一时段两种配置都比上午的 1.35 秒慢，原因是与游戏争用 GPU，与共用无关。

**输出一致性**（dancing.jpg 原图 + 水平翻转，最大绝对差）

| 输出 | GPU 自身噪声（两次不共用对比） | 共用 vs 不共用 |
|---|---|---|
| 顶点 / 关节坐标（米） | 0.7–1.4 × 10⁻⁴ | 0.4–1.4 × 10⁻⁴ |
| 关节全局旋转矩阵 | 1.6–4.2 × 10⁻⁴ | 1.6–3.5 × 10⁻⁴ |
| 2D 关键点（像素） | 0.05–0.09 | 0.02–0.07 |
| 身体/手部姿态参数 | ≤ 2.2 × 10⁻³ | ≤ 4.0 × 10⁻³（约 0.2°） |
| 相机平移 / 焦距 | ~10⁻⁵ / 0 | ~10⁻⁵ / 0 |

共用前后的差异与 GPU 非确定性噪声同量级（亚毫米、亚像素），可视为一致。

复测：`scripts/bench_sam3d.py --precision bf16 [--no-share-mhr]`。

## 低显存 / CPU 模式（2026-10-25）

`scripts/verify_devices.py <图片...>`：每种配置在独立子进程里跑，测显存与速度，并两两比较输出。
测试图：真人照片、插画（926 号）、webp 照片；游戏同时运行。

| 配置 | 加载后 / 推理后显存 | 释放后残留 | 单张推理 |
|---|---|---|---|
| GPU bf16（原默认） | 2.65 / 2.75 GB | 0.1–0.2 GB | 0.9 s |
| GPU bf16 + MHR 放 CPU（新 GPU 默认） | 1.88 / 2.0 GB | 0.15 GB | 1.4 s |
| GPU fp32 | 3.7 / 3.76 GB | — | 1.4–1.9 s |
| CPU fp32（新 CPU 默认，i7 20 线程） | 0（不初始化 CUDA） | 0 | 10–16 s |

- 释放后的残留是 CUDA 运行时上下文，后端进程退出才归还；CPU 模式全程不初始化 CUDA
- 加载约 10 s（含读 2.5GB 权重）；模型先在 CPU 上组装再搬到显卡，加载期间不会出现重复 MHR 的显存峰值

**输出一致性**（重定向到 FF14 后的骨骼旋转差；"身体"不含手指）

| 比较 | 照片 | 插画 | webp 照片 |
|---|---|---|---|
| GPU bf16 两次运行（随机误差参照） | 最大 0.5° | 最大 9.3°（左腕） | 0° |
| MHR 放 CPU vs 放 GPU | 最大 0.6° | 0° | 0° |
| CPU fp32 vs GPU fp32 | 最大 0.35° | 最大 3.6°（左腕），平均 0.43° | 0.1° |
| GPU fp32 vs GPU bf16 | 最大 1.8° | 最大 20°（左腕），平均 1.7° | 最大 5°（右腕） |

- MHR 放 CPU 与设备本身（CPU/GPU）都不改变结果；差异主要来自骨干精度 bf16 / fp32，几乎全集中在手腕（j_te）
- 插画这张图本身不稳定：同一 GPU 配置跑两次左腕就差 9°（手部精修分支对微小数值差敏感）
- CPU 用 bf16 想对齐 GPU 默认结果：这台 CPU 没有 bf16 硬件，三张图十几分钟没跑完，放弃；CPU 固定用 fp32
- 加载改为内存映射读取权重、两个头只读一份 MHR：之前先把 2.5GB 权重整个读进内存，与游戏同跑时出现过 `MemoryError: bad allocation`

**后端端到端**（游戏运行中，经 FastAPI 调用）：识别后立即释放 → 显存残留 +126MB；空闲 4 秒释放 → 识别完 +1989MB、8 秒后 +110MB；
切到 CPU → 识别 16 s、显存不变；自动档门槛设得高于可用显存 → 自动用 CPU（fp32）。与游戏同跑时 GPU 单张 3.1–3.8 s（含 MHR 在 CPU）。
